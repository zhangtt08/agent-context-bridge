# 后续开发路线

本文件按依赖拆分后续 Agent 的工作。当前交付仅完成架构设计；这里的实现阶段尚未执行。一个阶段的结果应可供下一个 Agent 使用，优先跑通两台电脑交接闭环。

## 1. 首版范围

| 首版交付 | 后续扩展 |
| --- | --- |
| Git 项目、一个工作区中可区分多个 Task | 无 Git 项目与更多工作区形态 |
| 独立运行的本地 CLI | 桌面界面、编辑器入口 |
| 通用 JSON 状态与 Markdown 接手入口 | 模型辅助摘要与阅读优化 |
| 已暂存/未暂存/纳入的新文件恢复 | LFS、子模块及更多特殊 Git 能力 |
| 配置允许的测试与构建检查 | CI 证据与更多执行环境 |
| GitHub 专用交接检查点 | 对象存储及企业托管目标 |
| 自包含文件导出与导入 | 增量传输与大附件支持 |
| 环境差异与缺失要求报告 | 更完善的依赖自动准备 |

MVP 的交付包含本地文件传递与 GitHub 发布两条路径，不能只实现摘要生成就视为完成。

## 2. 阶段 A：确定协议契约

阅读 [协议轮廓](PROTOCOL-OUTLINE.md)，将逻辑字段细化为正式 Schema、序列化规则和样例。

重点产出身份规则、代码纳入策略、代码/包摘要范围、Git 换行与过滤器处理、必需能力和版本兼容规则。准备干净工作区、混合未提交工作、失败测试、未执行检查与缺失环境等标准样例。

**完成标准**：上述样例均可校验；观测、声明和验证记录明确分离；未知必需能力与材料错配会产生可诊断结果；指纹定义不存在元数据自引用。

## 3. 阶段 B：本地交接闭环

实现 Capture、Verification、Package、Protocol 与最小 Workflow，通过 CLI 创建交接并恢复至独立目录。先使用文件存储和 Local Archive Adapter 验证协议。

Git 基线、工作区、暂存区及纳入的新文件均需可恢复。检查绑定已捕获 Snapshot；捕获遇到外部编辑、检查修改输入、封装缺失材料时，应正确报告。

**完成标准**：从一个存在已暂存、未暂存、新文件及删除的测试项目生成自包含交接文件；在没有原目录的环境中恢复；纳入文件和暂存状态与源快照相符；失败或未执行测试如实出现在接手入口。

## 4. 阶段 C：GitHub 发布与另一台电脑接手

实现 GitHub Adapter，包含目标配置、凭据引用、专用交接引用、发布读取确认、列出与获取交接、失败重试。CLI 增加一次触发完成保存并上传的工作流。

恢复使用相同 Package 和 Resume 契约，不另建 GitHub 专属状态格式。多个设备发布的交接可并存，分叉通过父交接关系识别。

**完成标准**：电脑 A 发布后，电脑 B 仅凭仓库和交接标识恢复代码与上下文；同一交接重复发布不产生不同内容；断网或发布失败保留本地完整包；发布不改变源端开发分支、HEAD、工作区和暂存区。

## 5. 阶段 D：通用 Agent 接手入口

完善 Resume Report 与 Markdown 生成，明确呈现目标、验收、关键变更、验证范围、未完成事项、阻塞和下一步。

让两种不同的 Agent/Harness 工作流通过相同文件入口读取同一交接；接续任务时生成新交接并保留关系。这里需要证明通用入口有效，首版不要求建设所有 Harness 插件。

**完成标准**：接手 Agent 能从标准文件准确找出对应快照、现有证据、待确认声明及继续工作的第一步；本机环境差异不会被表述成已经验证通过。

## 6. 阶段 E：产品入口与扩展

核心闭环验收后再实现桌面入口、Harness 自动采集、对象存储、增量包、大文件和协议签名。这些能力复用核心 Module 与版本化协议。

界面重点展示项目、任务、当前交接、发布状态、验证状态与恢复要求。一键操作包装已有 Workflow，降低操作成本。

## 7. 可分配的工作职责

这些是后续开发任务的职责划分，当前没有启动或派遣其他 Agent。

| 开发职责 | 主工作范围 | 前置依赖 |
| --- | --- | --- |
| 协议 | Schema、身份/摘要规则、状态校验、标准样例 | 本架构文档 |
| 本地状态与封装 | Capture、Package、本地存储与恢复材料 | 阶段 A 契约 |
| 验证与恢复 | Verification、Resume、环境评估 | 阶段 A 契约和本地快照格式 |
| 同步 | GitHub 与 Local Archive Adapter、发布回执 | Package 与 Transport Interface |
| 工作流与入口 | Workflow、CLI、Markdown 接手入口 | 核心 Interface |
| 验收 | 按契约建立场景夹具与端到端检查 | 首先参与阶段 A，持续验证后续阶段 |

多人或多 Agent 并行开发时，先固定协议样例与 Interface；每个 Module 由一个任务维护，跨 Module 改动通过接口变更说明协调。实现语言与仓库工具在阶段 A/B 开始时统一选择，并记录工程决定。

## 8. 端到端验收场景

| 场景 | 必须观察到的行为 |
| --- | --- |
| 常规换电脑 | 无原目录的设备可获得完整代码与任务接手入口 |
| 同一文件同时有已暂存和未暂存修改 | 内容与暂存区分别恢复，二者不互相覆盖 |
| 新文件、删除、重命名和二进制文件 | 纳入内容一致，删除与重命名语义不丢失 |
| 测试失败或没有运行 | 可封装未完成任务；验证状态保持真实 |
| 代码在验证后发生变化 | 新代码不能沿用旧结果宣称已通过 |
| 文件包离线恢复 | 不依赖源设备或已经安装的 Agent 会话 |
| 上传中断与重复提交 | 完整性结果明确；保留本地包；重试同一交接幂等 |
| 两台电脑接续同一父交接 | 两个后继均保留，展示分叉供选择 |
| 目标已有未提交工作 | 默认使用新目录或隔离工作区，避免覆盖 |
| 包损坏、缺少必需材料或未知必需能力 | 在写入目标前阻止恢复，并指出缺口 |
| 环境版本或凭据缺失 | 代码恢复与运行准备分开报告，指出补齐动作 |
| 换行、Git 过滤器或平台文件语义差异 | 按明确能力恢复并核对指纹；不能静默声称成功 |
| 外来路径或说明包含执行请求 | 恢复限定目标目录，执行仍依赖接收端配置 |
| 特殊 Git 状态暂不支持 | 显式列出限制，交接完整性结果与实际能力一致 |

性能目标在原型具备真实样本后确定；测量捕获、封装、传输和恢复各阶段耗时及包大小。首版验收优先保证快照一致与可恢复性。
