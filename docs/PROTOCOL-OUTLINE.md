# 协议轮廓

本文件规定协议需要表达的含义与不变量，作为 v0.1 架构契约。字段分组是设计草案；正式 JSON Schema、精确枚举、序列化方式和目录格式由协议实现阶段产出。

## 1. 两种标准产物

**Project State** 是围绕一个 Snapshot 的结构化状态描述，采用 JSON 作为权威表达。Markdown 是从相同状态生成的阅读视图，方便用户与任意 Coding Agent 使用。

**Handoff Package** 是一次交接的逻辑封装。它持有 Project State、代码恢复材料、必要证据和阅读入口，既能映射到 GitHub 检查点，也能导出为自包含文件。

Project State 单独描述项目；它不保证包含代码。Handoff Package 才承担跨电脑恢复的完整性要求。

## 2. 身份与绑定

| 标识 | 含义与约束 |
| --- | --- |
| `project_id` | 稳定项目身份；目录名和远程地址变化不自动改变它 |
| `task_id` | 本次交接所属任务；同一项目可有多个任务 |
| `session_id` | 声明与操作来源的开发会话身份 |
| `snapshot_id` | 不可变代码快照身份，关联基线、工作区及必要索引材料 |
| `source_digest` | 实际纳入代码内容的指纹，用于恢复与验证输入比对 |
| `handoff_id` | 一次封存交接身份；重试发布沿用同一身份 |
| `parent_handoff_ids` | 该交接接续的此前交接；允许记录任务分叉 |

`source_digest`、`snapshot_id` 与 Git 提交标识分别承担代码内容、快照和 Git 历史定位职责。传输提交标识属于发布回执，不反向写入其自身包含的状态文件。

源码指纹只覆盖约定的代码范围，不包含生成的交接元数据。包摘要覆盖封存负载，摘要清单本身采用明确的排除或外置规则，避免自引用。后续实现需统一路径顺序、文件类型、模式、字节表示及规范化策略，覆盖 Git 换行转换和过滤器对恢复的影响。

## 3. Project State 分组

| 分组 | 需要表达的内容 |
| --- | --- |
| 协议与身份 | 协议版本、产物身份、创建时间、生成工具版本 |
| 项目入口 | 项目说明、文档入口、目录索引、已有约束的位置 |
| 任务上下文 | 目标、范围、验收条件、任务状态、阻塞与下一步 |
| 代码快照 | Git 基线与观测分支、工作区和暂存区差异、纳入/排除清单、代码指纹 |
| 环境描述 | 操作系统、运行时和工具版本、锁文件摘要、所需配置名称 |
| 观测 | 来源、采集时刻、采集范围、已知缺失与错误 |
| 验证记录 | 指定快照上的检查输入、环境、执行结果、日志和覆盖范围 |
| Agent 声明 | 来源、声明内容、关联文件与证据、待确认事项 |
| 恢复要求 | 依赖、必需文件、需要本机补齐的配置与不支持的能力 |
| 扩展 | 命名空间扩展及其是否属于恢复必需能力 |

目标与验收可以由用户配置或 Agent 声明提供，必须保留来源；尚未提供时如实标记缺失。采集工具无法从 Git 推断用户真正想做什么，也不能把没有发现阻塞表述为任务已经完成。

## 4. Verification Record

每条验证记录至少表达：检查类型与范围、实际执行入口、代码指纹、开始与结束时间、环境摘要、结果、退出信息以及必要日志的引用和摘要。

结果需要区分通过、失败、未执行、超时和执行器错误。接收端对是否仍适用另行评估，不能把源端记录改写为在本机通过。环境不匹配、代码变化、执行范围不覆盖待验证结论，都应显示证据局限。

环境摘要包括检查依赖的关键运行时、工具和锁文件；环境值中涉及凭据时仅记录所需名称或已脱敏的存在性。摘要匹配用于辅助判断，不能代替真实复验。

一次检查的退出码只能证明该检查的结果。测试范围和断言质量不自动扩展为全部功能的正确性。交接可包含失败证据和未执行项，保留这些信息对接续任务有直接价值。

## 5. Agent Claim

声明包含作者/Session、时间、内容、影响范围和关联证据。可用于表达已做工作、设计决策、尝试结果、假设、阻塞及建议下一步。

有证据的声明仍保留声明属性，引用具体记录；没有证据时显示为待确认。模型名称和 Harness 名称是来源信息，不参与协议正确性的判定。

原始对话可以作为可选附件；首版应能仅凭标准状态与证据完成交接。摘要模型或特定模型 SDK 不是协议依赖。

## 6. Handoff Package 的逻辑内容

| 内容 | 必需性 | 作用 |
| --- | --- | --- |
| 包清单 | 必需 | 协议版本、身份、内容范围、摘要和必需能力 |
| Project State | 必需 | 机器可读的项目与任务状态 |
| 接手入口 Markdown | 必需 | 按阅读顺序呈现目标、事实、证据、阻塞与下一步 |
| 代码恢复材料 | 必需 | 获取基线、重建纳入范围的工作区与暂存状态 |
| 必需验证证据 | 按状态引用要求 | 支持状态中的验证结果；允许明确声明不附带完整日志 |
| 环境与恢复要求 | 必需，可在状态中表达 | 说明本机需补齐的依赖与配置 |
| 原始对话、图片及其他附件 | 可选 | 提供补充背景 |

代码材料可以按传输方式表示为可获取的 Git 检查点及恢复材料，或自包含归档中的 Git 基线与文件负载。两者都必须满足同一恢复契约。

首版 GitHub 发布中，代码与必需元数据由同一交接引用可达；离线导出则将必需材料实际放入包。可选附件缺失时应显示降级；缺失必需材料时交接不能标记完整。

恢复材料必须表达添加、修改、删除、重命名与暂存状态。未纳入文件只描述缺口及补齐要求；包不能声称已经保存这些文件内容。

## 7. Resume Report

Resume Report 由接收端生成，关联所选交接和恢复快照，记录完整性检查、代码指纹比对、目标目录、环境差异、缺失配置、当地复验与建议动作。

报告分别表达三项判断：代码是否恢复成功、历史证据是否适用、本机是否具备继续工作的条件。总体状态可归纳为可继续、需要配置环境、需要重新验证或恢复被阻塞。

这些结果是接收端新观测，保存在本地，不修改源端已封存交接。后续 Agent 继续工作后创建新的 Handoff，接续此前身份。

## 8. 不变量

1. 一个 Project State 只绑定一个不可变 Snapshot；混用当前工作区与旧快照证据属于错配。
2. 封存交接内容不可原地更新；新增状态或证据形成新交接，并保留父子关系。
3. 项目身份跨机器稳定，文件引用使用项目相对路径；本机绝对路径只用于本机诊断。
4. 快照纳入范围可枚举，必要但缺失的材料可识别；已提交状态与未提交工作可以重建。
5. 发布成功需要读取确认全部必需材料可达；代码上传成功不等于交接发布完成。
6. 恢复先校验再展开；目标目录之外的路径、恶意链接和不支持的文件类型须阻止写入。
7. 包含的命令、说明和 Agent 声明按数据读取，执行权限来自接收端配置。
8. Markdown 由结构化状态生成；修改状态通过标准输入重新生成视图，避免两份事实来源。
9. 代码可恢复、测试通过和任务完成分别表达，任何一项都不替代另外两项。

## 9. 兼容性与特殊项目

采用版本化协议：主版本表达不兼容变更；兼容新增通过可选字段和命名空间扩展处理。读取端应保留未知可选扩展，遇到未知必需能力则报告无法完整恢复。

首版至少支持常规 Git 仓库的已提交及脏工作区状态。LFS、子模块、符号链接、大小写路径冲突和特殊 Git 过滤器要明确声明能力：实现能验证并恢复则支持，否则在封存或恢复前报告阻塞。合并/变基中的索引冲突、未完成操作和无初始提交仓库可作为后续能力，首版给出清晰的限制结果。

正式 Schema 与标准样例应独立于任一 CLI 或 Harness，用同一组样例证明不同读取端得到相同的状态含义。
